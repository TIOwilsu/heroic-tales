# 12 — Security

Use server-side secrets only; keep keys in deployment secret configuration and out of source, client bundles, logs, fixtures, screenshots, and error messages. Apply least privilege, ownership checks, input validation, output encoding, rate limits, request size limits, dependency review, and secure headers appropriate to the selected deployment configuration.

Protect draft and approved character data in transit and at rest using platform capabilities. Define retention, deletion, export, account recovery, abuse reporting, audit access, and incident response before production; these are `TBD`.

## Self-managed authentication

The backend owns credential verification, token creation, and token validation, but does not store access tokens, refresh tokens, or token digests. Tokens must be self-contained and verifiable using backend-only signing/verification configuration. The client stores the issued tokens and sends access tokens only through the `Authorization: Bearer` header. Refresh tokens require a defined rotation, reuse-detection, revocation, and client-storage strategy before production; these controls cannot depend on a backend token store under the approved design. Passwords must be hashed with a memory-hard password-hashing algorithm and must never be stored, returned, logged, or included in telemetry. Access tokens, refresh tokens, authorization headers, signing keys, password-reset material, and authentication payloads are secrets and must not appear in logs, errors, fixtures, screenshots, URLs, or source control.

Authentication checks must distinguish between an unauthenticated request and an authenticated request that does not own a resource, while avoiding resource-existence leakage. Every protected read or mutation must perform an ownership check before accessing account-owned data. Access-token expiration, refresh-token rotation, reuse detection, revocation, password recovery, email verification, password policy, client persistence, and roles are `TBD` and require security review before production. Backend token storage is explicitly excluded from the design.

Threat-model prompt injection, malicious character text, cross-tenant access, anonymous provider abuse, cost exhaustion, image misuse, and D&D content leakage. Guest generation must have server-side rate limiting, request bounds, safety checks, and cost controls even though authentication is not required. Security tests must cover authorization boundaries and secret handling.

Required authentication tests include invalid credentials, missing/expired/invalid access tokens, self-contained token validation without backend token persistence, refresh-token rotation and reuse detection if approved, password/token/signing-secret non-disclosure, authenticated access to owned data, rejection of cross-owner access, safe authorization-header handling, and continued guest access to generation and download workflows. Revocation and forced logout behavior must be tested once a stateless-compatible strategy is approved.
